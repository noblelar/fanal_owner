# Coordinated Fanal Platform Releases (Phase 6)

## Outcome

Phase 6 treats Fanal API, Fanal Main, and Fanal Owner as independently versioned components that are deployed as one tested platform combination. A platform release has its own stable Semantic Version and a deterministic manifest containing the exact image digest, component version, and full Git revision for all three components.

The Owner repository is the release coordinator. Actual manifests are generated by the manually dispatched **Coordinate Fanal Platform Release** workflow and retained as workflow artifacts. They are not committed to a component repository, which avoids a circular dependency between a manifest and the Owner commit it identifies.

## Normal pipeline

1. Merge reviewed component changes to each component's `master` branch.
2. Each component workflow runs its quality gate and publishes immutable full-SHA and version-SHA images.
3. The old component-only deployment job stays skipped unless the break-glass repository variable `FANAL_LEGACY_COMPONENT_AUTO_DEPLOY=true` is deliberately created.
4. Copy the exact digest, version, and full revision from each successful build summary into **Coordinate Fanal Platform Release**.
5. Select `deploy-candidate`. The workflow validates the platform manifest and sends it to EC2 through SSM.
6. EC2 saves the previous three-component combination, deploys API, Main, then Owner under one deployment lock, validates every OCI label and version endpoint, reloads Nginx through the component deployer, and records the candidate.
7. New functionality remains behind the school-scoped feature rollout contract. Start at `test` with only the Demo School's immutable database ID.
8. After candidate evidence is accepted, run the same workflow with `promote-candidate` and exactly the same manifest values. EC2 rejects any artifact difference. Promotion does not rebuild or redeploy an image.

## Platform operations

| Workflow operation | Effect |
| --- | --- |
| `deploy-candidate` | Transactionally deploys and verifies the exact manifest; stores the prior platform combination for rollback. |
| `verify-candidate` | Verifies the running containers, deployment state, labels, revisions, endpoints, and Nginx configuration without changing containers. |
| `promote-candidate` | Requires an exact match with the stored tested candidate, re-verifies it, and records it as stable. |
| `rollback-candidate` | Restores and verifies the three-component combination captured before the candidate deployment. |

`platform_release_env` must have a required reviewer and the same `AWS_ROLE_ARN`, `AWS_REGION`, and `EC2_INSTANCE_ID` values used for the existing SSM deployment. Docker Hub credentials are not required by this workflow because EC2 pulls public image digests using the existing component deployer.

## Server files

Install these files together:

- `/home/ubuntu/fanal/scripts/deploy-component.sh`
- `/home/ubuntu/fanal/scripts/deploy-platform-release.sh`

The coordinated script requires Bash, Docker Compose, `base64`, `curl`, `diff`, `flock`, `jq`, and `sed`. It reads the Phase 5 component state files and writes:

- `deployments/platform-candidate.json`: exact candidate manifest.
- `deployments/platform-rollback.json`: previous coordinated component combination.
- `deployments/platform.env`: current platform version, state, and component identities.

## School-scoped feature rollout

Every new tenant-visible feature must use the same stable uppercase feature key in both Main and API. Main evaluates it with `getSchoolFeatureRolloutDecision`; API evaluates it with `SchoolFeatureRolloutService`. Both containers receive the same variables from `.env.prod`:

```text
FEATURE_ROLLOUTS__NEW_FEATURE__ENABLED=false
FEATURE_ROLLOUTS__NEW_FEATURE__RELEASE_APPROVED=false
FEATURE_ROLLOUTS__NEW_FEATURE__STAGE=off
FEATURE_ROLLOUTS__NEW_FEATURE__TEST_SCHOOL_IDS=
FEATURE_ROLLOUTS__NEW_FEATURE__PILOT_SCHOOL_IDS=
FEATURE_ROLLOUTS__NEW_FEATURE__PERCENTAGE=
```

The API must derive the school ID from the authenticated server context. Never authorize a feature using a school ID supplied only by a request body, query string, browser variable, school name, or email domain. Main must resolve the same authenticated school ID on the server. A UI-only gate is not a security boundary; protected API operations must also evaluate the rollout.

The stage progression is `off` → `test` → `pilot` → `percentage` → `general`. Test and pilot cohorts remain enabled at later stages. Missing approvals, missing school identity, invalid percentages, and malformed active configuration all fail closed. Cohort diagnostics report counts and reasons, never school identifiers.

The existing Admin Workspaces rollout retains its more specific, evidence-gated controls. It is not silently migrated to the generic contract in Phase 6.

## Shared database rule

The Demo School and production schools may remain in one database because feature access is determined by the authenticated `School.Id`, not by a separate database. Candidate migrations must follow expand/contract deployment:

1. Add nullable columns, new tables, or backward-compatible indexes first.
2. Deploy code that works with both the old and expanded schema.
3. Backfill separately and observably.
4. Remove old schema only in a later stable release after all old code paths are retired.

Never deploy a candidate migration that renames/drops a column or makes a new column mandatory while the prior stable containers may still need the earlier schema.

## Emergency path

The repository variable `FANAL_LEGACY_COMPONENT_AUTO_DEPLOY=true` re-enables independent deployment in that repository. It exists only for a documented emergency. Remove it immediately after the incident; any component-only deployment invalidates the currently tested platform combination and requires a new candidate manifest.
